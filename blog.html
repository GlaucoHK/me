Por que escrevi um agente de monitoramento em NimWhy I wrote a monitoring agent in Nim

Comecei a desenhar um agente de telemetria de hardware desses que ficam residentes na maquina coletando RAM, CPU, GPU, disco e inventario. A primeira pergunta que veio na cabeca foi a obvia: por que nao usar uma das dezenas de solucoes ja prontas?

A resposta saiu dos requisitos. O agente precisava ser leve, ou seja, rodar em maquinas modestas sem competir por recursos com a aplicacao monitorada. Tambem precisava ser auto-suficiente, sem runtime pesado pra instalar. E flexivel o bastante pra coletar dados de fontes muito diferentes, desde APIs do Windows ate utilitarios de terceiros instalados no host. Python ficou descartado pelo runtime. Go era opcao, so que eu queria algo ainda mais enxuto no binario final. Rust seria excelente, mas a curva de iteracao era mais lenta do que eu precisava pra esse projeto especifico. Nim apareceu como o ponto doce: sintaxe limpa (compila pra C nos bastidores), binarios estaticos compactos, FFI direto pra APIs nativas, e velocidade comparavel a C++.

O que o agente coleta

O escopo da coleta cobre o que importa pra inventario e diagnostico:

  • RAM total, uso por processo, paginacao e pressao de memoria.
  • CPU: modelo, nucleos, frequencia, temperatura, uso por core.
  • GPU: identificacao, VRAM, temperatura, drivers ativos.
  • Armazenamento: drives, SMART, saude, temperatura, espaco.
  • Inventario: placa-mae, BIOS, sistema operacional, software instalado.

Cadeia de fallbacks

A parte mais interessante do projeto, e a que justifica boa parte do trabalho, e a cadeia de fallbacks. Nenhuma fonte unica cobre tudo de forma confiavel em maquinas variadas, entao a estrategia foi montar uma cascata em tres niveis.

Primeiro, APIs nativas do sistema operacional. Windows API (WMI, Performance Counters, registry) porque sao gratuitas, ja estao ali e nao exigem dependencias externas.

Segundo, utilitarios locais especializados quando presentes. CrystalDiskInfo pra saude de disco, LibreHardwareMonitor pra sensores que a API do SO nao expoe (temperaturas de chip, voltagens, sensores de placa-mae menos comuns). O agente detecta a presenca deles e parseia a saida, sem incorporar codigo de terceiros.

Terceiro, degradacao graciosa. Quando nada esta disponivel pra uma metrica especifica, ela e marcada como indisponivel em vez de quebrar a coleta inteira. Um host sem GPU dedicada nao deve fazer o agente travar.

Esse desenho importa porque ambientes reais sao bagunca. Maquinas com BIOS travado, agentes de seguranca que bloqueiam WMI, hosts sem privilegios administrativos, drivers desatualizados. Cada degrau da cascata e uma chance de ainda extrair dado util onde uma abordagem monolitica ja teria desistido.

Pegada de recursos

O binario final fica em um intervalo de poucos megabytes, sem dependencias de runtime instaladas. O uso de RAM em operacao normal e contido o suficiente pra rodar em paralelo a cargas de trabalho reais sem se fazer notar. Esse e exatamente o ponto de um agente de monitoramento: estar la sem atrapalhar.

Por que vale o esforco

Construir o proprio agente em vez de adotar um pronto so faz sentido em alguns casos. Quando voce precisa de controle sobre a forma da coleta, por exemplo. Ou quando o ambiente alvo tem restricoes especificas. Ou ainda quando o codigo precisa ser mantido fechado. Nesses cenarios, a combinacao Nim com cascata de fallbacks rende um produto pequeno, robusto e independente. Esse tipo de projeto ensina muito sobre interoperabilidade entre sistemas, e o resultado final tem cara de coisa propria, nao de wrapper em cima de wrapper.

I started designing a hardware telemetry agent, the kind that stays resident on the machine collecting RAM, CPU, GPU, disk and inventory data. The obvious first question came up: why not use one of the dozens of off-the-shelf solutions?

The answer came from the requirements. The agent had to be lightweight, meaning it should run on modest hardware without competing for resources with the monitored application. It also had to be self-contained, with no heavy runtime to install. And flexible enough to pull data from very different sources, from Windows APIs all the way to third-party utilities installed on the host. Python was out because of the runtime. Go was an option, but I wanted something even leaner in the final binary. Rust would have been excellent, but the iteration curve was slower than I needed for this specific project. Nim hit the sweet spot: clean syntax (it compiles to C under the hood), compact static binaries, direct FFI to native APIs, and speed comparable to C++.

What the agent collects

The collection scope covers what matters for inventory and diagnostics:

  • RAM: total, per-process usage, paging and memory pressure.
  • CPU: model, cores, frequency, temperature, per-core usage.
  • GPU: identification, VRAM, temperature, active drivers.
  • Storage: drives, SMART, health, temperature, free space.
  • Inventory: motherboard, BIOS, OS, installed software.

Fallback chain

The most interesting part of the project, and what justifies a lot of the work, is the fallback chain. No single source reliably covers everything across varied machines, so the strategy was to build a three-tier cascade.

First, native OS APIs. Windows API (WMI, Performance Counters, registry) because they're free, already there, and don't require external dependencies.

Second, specialized local utilities when present. CrystalDiskInfo for disk health, LibreHardwareMonitor for sensor data the OS API doesn't expose (chip temperatures, voltages, less common motherboard sensors). The agent detects their presence and parses their output, without bundling third-party code.

Third, graceful degradation. When nothing is available for a specific metric, it gets marked as unavailable instead of breaking the whole collection. A host with no dedicated GPU shouldn't lock up the agent.

This design matters because real environments are messy. Machines with locked BIOS, security agents that block WMI, hosts without admin privileges, outdated drivers. Each step in the cascade is a chance to still extract useful data where a monolithic approach would have already given up.

Resource footprint

The final binary sits in the low single-digit megabytes, with no runtime dependencies installed. RAM usage in normal operation stays low enough to run alongside real workloads without making itself noticed. That's exactly the point of a monitoring agent: being there without getting in the way.

Why it's worth the effort

Writing your own agent instead of adopting a pre-built one only makes sense in a few cases. When you need control over the shape of collection, for instance. Or when the target environment has specific constraints. Or when the code needs to be kept closed. In those cases, the Nim plus fallback-cascade combo yields a small, robust, independent product. This kind of project teaches a lot about cross-system interoperability, and the final result feels like something of your own, not a wrapper on top of a wrapper.

Anatomia de uma exposicao de diretorioAnatomy of a directory exposure

Listagem de diretorio (directory listing, ou "open directory") e um dos bugs mais antigos da web. Configuracao errada de servidor permite que qualquer um navegue pela estrutura de pastas como se fosse o Explorer do Windows. Voce vai num caminho qualquer do dominio, sem saber o que tem ali, e o servidor te entrega uma lista de arquivos. As vezes os arquivos sao inocentes. As vezes nao. E em 2026, isso ainda acontece com mais frequencia do que deveria.

Quero falar de uma tecnica especifica pra encontrar esses diretorios sensiveis, porque o jeito tradicional (forca bruta com wordlist) e ruidoso, lento e cheio de falso positivo. Tem um caminho mais elegante: observar os redirects que acontecem depois do login.

Por que esse bug ainda existe

A causa raiz quase sempre e uma das tres. Um, configuracao default do servidor web (Apache, nginx, IIS) que veio com listagem habilitada e ninguem desligou. Dois, um diretorio que foi criado pra hospedar algum recurso publico (uploads, relatorios, exports) e nunca recebeu o tratamento de seguranca que o resto da aplicacao tem. Tres, ambiente de desenvolvimento ou staging que vazou pra producao com configuracoes mais permissivas.

Em todos os casos, o problema nao e o servidor em si. E que alguem assumiu que ninguem ia procurar.

A tecnica: redirects pos-login

Quando voce faz login num sistema corporativo, o servidor frequentemente te redireciona pra algum caminho interno antes de chegar na pagina final. Esse caminho intermediario as vezes e a homepage da area logada, outras vezes e um endpoint de roteamento, e em alguns casos e um diretorio inteiro que serve de base pra navegacao da area autenticada.

O ponto chave: esse caminho aparece no historico de requisicoes do seu navegador (ou no Burp Suite, no DevTools, em qualquer proxy). Voce ve /login, depois /auth/callback, depois /painel/inicio.html. A pasta /painel/ e o diretorio base da area logada. Bater nela diretamente, sem o inicio.html, e o teste obvio. Bater nas variantes (/painel/relatorios/, /painel/uploads/, /painel/backup/) e o passo seguinte.

Esse caminho normalmente nao aparece em wordlists genericas, porque e especifico daquela aplicacao. Mas o redirect te entrega o nome de mao beijada.

Outras superficies que entregam estrutura

O redirect pos-login e o ponto mais rico, mas nao e o unico. Vale combinar com algumas outras fontes ao longo da analise.

  • robots.txt as vezes lista caminhos que o dono nao quer indexados, ou seja, e mapa do tesouro pra quem procura.
  • sitemap.xml com sorte enumera paginas internas que voce nao chegaria so navegando.
  • Source maps (.map) de JavaScript de producao podem revelar a estrutura de pastas do projeto inteiro.
  • Comentarios HTML deixados em paginas publicas (links comentados, caminhos de teste, TODOs com URL).
  • Headers HTTP como X-Powered-By, Server e mensagens de erro que vazam paths absolutos.
  • Paginas de erro 404 customizadas que mostram parte do path requisitado.

Cada uma sozinha quase nunca da o bug. Combinadas com o redirect pos-login, formam o mapa.

O que costuma estar la dentro

Quando a listagem esta ativa, o conteudo varia muito. Em ambientes onde isso vira problema serio, e comum encontrar planilhas com dados internos da empresa (faturamento, clientes, listas de funcionarios), backups antigos de banco de dados, configuracoes (.env, credenciais hardcoded), logs com dados sensiveis no meio, ou arquivos temporarios que ninguem lembra de apagar. Em CVSS, isso geralmente bate em High (7+) quando o conteudo contem PII ou credenciais.

Mitigacao

A correcao tecnica e trivial. Em Apache, Options -Indexes no diretorio. Em nginx, garantir que autoindex esteja em off (que e o padrao, mas vale checar). Em IIS, desabilitar "Directory Browsing" nas configuracoes do site.

A correcao organizacional e mais dificil, e e onde fica o trabalho de verdade. Adotar uma postura de deny-by-default na infraestrutura, separar com clareza ambientes de desenvolvimento e producao, e fazer scans periodicos pelo proprio perimetro sao praticas que custam pouco e cortam essa classe de bug na raiz.

Por que vale escrever sobre isso

Esse tipo de bug nao tem charme. Ninguem escreve sobre exposicao de diretorio querendo virar destaque na DEF CON. Mas ele continua aparecendo em auditoria atras de auditoria, e e responsavel por uma fatia consideravel de vazamentos de dados em empresas que tem coisas mais sofisticadas pra se preocupar. Pesquisador que olha pro basico antes do exotico costuma achar mais bugs do que pesquisador que pula direto pra cadeia de exploit complexa. A maturidade em seguranca passa por levar a serio o que parece simples demais pra dar problema.

Directory listing (or "open directory") is one of the oldest bugs on the web. A server misconfiguration lets anyone browse the folder structure like Windows Explorer. You go to any path on the domain without knowing what's there, and the server hands you a file list. Sometimes the files are harmless. Sometimes they aren't. And in 2026, this still happens more often than it should.

I want to talk about a specific technique for finding sensitive directories, because the traditional approach (brute-force with wordlists) is noisy, slow, and full of false positives. There's a more elegant path: observe the redirects that happen after login.

Why this bug still exists

The root cause is almost always one of three. One, default web server configuration (Apache, nginx, IIS) that shipped with listing enabled and nobody turned it off. Two, a directory created to host some public resource (uploads, reports, exports) that never got the security treatment the rest of the application has. Three, a development or staging environment that leaked into production with more permissive settings.

In every case, the problem isn't the server itself. It's that someone assumed nobody would look.

The technique: post-login redirects

When you log into a corporate system, the server often redirects you through some internal path before reaching the final page. That intermediate path is sometimes the landing page of the logged area, sometimes a routing endpoint, and in some cases an entire directory that serves as the base for navigation in the authenticated area.

The key point: that path shows up in your browser's request history (or in Burp Suite, DevTools, any proxy). You see /login, then /auth/callback, then /dashboard/home.html. The /dashboard/ folder is the base directory of the logged area. Hitting it directly, without the home.html, is the obvious test. Hitting the variants (/dashboard/reports/, /dashboard/uploads/, /dashboard/backup/) is the next step.

That path usually doesn't appear in generic wordlists because it's specific to that application. But the redirect hands you the name on a silver platter.

Other surfaces that leak structure

The post-login redirect is the richest source, but not the only one. It pays to combine it with a few other inputs throughout the analysis.

  • robots.txt sometimes lists paths the owner doesn't want indexed, which is basically a treasure map for someone looking.
  • sitemap.xml with luck enumerates internal pages you wouldn't reach by just browsing.
  • Source maps (.map) for production JavaScript can reveal the project's entire folder structure.
  • HTML comments left on public pages (commented-out links, test paths, TODOs with URLs).
  • HTTP headers like X-Powered-By, Server, and error messages that leak absolute paths.
  • Custom 404 error pages that echo back part of the requested path.

Each one alone rarely gives you the bug. Combined with the post-login redirect, they form the map.

What's usually in there

When listing is active, content varies a lot. In environments where this becomes a serious issue, it's common to find spreadsheets with internal company data (revenue, customers, employee lists), old database backups, configurations (.env, hardcoded credentials), logs with sensitive data mixed in, or temporary files nobody remembers deleting. On CVSS, this usually scores High (7+) when the content contains PII or credentials.

Mitigation

The technical fix is trivial. In Apache, Options -Indexes on the directory. In nginx, make sure autoindex is set to off (which is the default, but worth checking). In IIS, disable "Directory Browsing" in the site settings.

The organizational fix is harder, and that's where the real work lies. Adopting a deny-by-default posture across the infrastructure, separating development and production environments cleanly, and running periodic scans against your own perimeter are practices that cost little and cut this class of bug at the root.

Why it's worth writing about

This kind of bug has no charm. Nobody writes about directory exposure hoping to land a DEF CON spotlight. But it keeps showing up in audit after audit, and it's responsible for a meaningful slice of data leaks at companies that have far more sophisticated things to worry about. A researcher who looks at the basics before the exotic tends to find more bugs than one who jumps straight to complex exploit chains. Maturity in security goes through taking seriously what looks too simple to cause trouble.
