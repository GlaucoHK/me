Por que escrevi um agente de monitoramento em NimWhy I wrote a monitoring agent in Nim

Comecei a desenhar um agente de telemetria de hardware desses que ficam residentes na maquina coletando RAM, CPU, GPU, disco e inventario. A primeira pergunta que veio na cabeca foi a obvia: por que nao usar uma das dezenas de solucoes ja prontas?

A resposta saiu dos requisitos. O agente precisava ser leve, ou seja, rodar em maquinas modestas sem competir por recursos com a aplicacao monitorada. Tambem precisava ser auto-suficiente, sem runtime pesado pra instalar. E flexivel o bastante pra coletar dados de fontes muito diferentes, desde APIs do Windows ate utilitarios de terceiros instalados no host. Python ficou descartado pelo runtime. Go era opcao, so que eu queria algo ainda mais enxuto no binario final. Rust seria excelente, mas a curva de iteracao era mais lenta do que eu precisava pra esse projeto especifico. Nim apareceu como o ponto doce: sintaxe limpa (compila pra C nos bastidores), binarios estaticos compactos, FFI direto pra APIs nativas, e velocidade comparavel a C++.

O que o agente coleta

O escopo da coleta cobre o que importa pra inventario e diagnostico:

  • RAM total, uso por processo, paginacao e pressao de memoria.
  • CPU: modelo, nucleos, frequencia, temperatura, uso por core.
  • GPU: identificacao, VRAM, temperatura, drivers ativos.
  • Armazenamento: drives, SMART, saude, temperatura, espaco.
  • Inventario: placa-mae, BIOS, sistema operacional, software instalado.

Cadeia de fallbacks

A parte mais interessante do projeto, e a que justifica boa parte do trabalho, e a cadeia de fallbacks. Nenhuma fonte unica cobre tudo de forma confiavel em maquinas variadas, entao a estrategia foi montar uma cascata em tres niveis.

Primeiro, APIs nativas do sistema operacional. Windows API (WMI, Performance Counters, registry) porque sao gratuitas, ja estao ali e nao exigem dependencias externas.

Segundo, utilitarios locais especializados quando presentes. CrystalDiskInfo pra saude de disco, LibreHardwareMonitor pra sensores que a API do SO nao expoe (temperaturas de chip, voltagens, sensores de placa-mae menos comuns). O agente detecta a presenca deles e parseia a saida, sem incorporar codigo de terceiros.

Terceiro, degradacao graciosa. Quando nada esta disponivel pra uma metrica especifica, ela e marcada como indisponivel em vez de quebrar a coleta inteira. Um host sem GPU dedicada nao deve fazer o agente travar.

Esse desenho importa porque ambientes reais sao bagunca. Maquinas com BIOS travado, agentes de seguranca que bloqueiam WMI, hosts sem privilegios administrativos, drivers desatualizados. Cada degrau da cascata e uma chance de ainda extrair dado util onde uma abordagem monolitica ja teria desistido.

Pegada de recursos

O binario final fica em um intervalo de poucos megabytes, sem dependencias de runtime instaladas. O uso de RAM em operacao normal e contido o suficiente pra rodar em paralelo a cargas de trabalho reais sem se fazer notar. Esse e exatamente o ponto de um agente de monitoramento: estar la sem atrapalhar.

Por que vale o esforco

Construir o proprio agente em vez de adotar um pronto so faz sentido em alguns casos. Quando voce precisa de controle sobre a forma da coleta, por exemplo. Ou quando o ambiente alvo tem restricoes especificas. Ou ainda quando o codigo precisa ser mantido fechado. Nesses cenarios, a combinacao Nim com cascata de fallbacks rende um produto pequeno, robusto e independente. Esse tipo de projeto ensina muito sobre interoperabilidade entre sistemas, e o resultado final tem cara de coisa propria, nao de wrapper em cima de wrapper.

I started designing a hardware telemetry agent, the kind that stays resident on the machine collecting RAM, CPU, GPU, disk and inventory data. The obvious first question came up: why not use one of the dozens of off-the-shelf solutions?

The answer came from the requirements. The agent had to be lightweight, meaning it should run on modest hardware without competing for resources with the monitored application. It also had to be self-contained, with no heavy runtime to install. And flexible enough to pull data from very different sources, from Windows APIs all the way to third-party utilities installed on the host. Python was out because of the runtime. Go was an option, but I wanted something even leaner in the final binary. Rust would have been excellent, but the iteration curve was slower than I needed for this specific project. Nim hit the sweet spot: clean syntax (it compiles to C under the hood), compact static binaries, direct FFI to native APIs, and speed comparable to C++.

What the agent collects

The collection scope covers what matters for inventory and diagnostics:

  • RAM: total, per-process usage, paging and memory pressure.
  • CPU: model, cores, frequency, temperature, per-core usage.
  • GPU: identification, VRAM, temperature, active drivers.
  • Storage: drives, SMART, health, temperature, free space.
  • Inventory: motherboard, BIOS, OS, installed software.

Fallback chain

The most interesting part of the project, and what justifies a lot of the work, is the fallback chain. No single source reliably covers everything across varied machines, so the strategy was to build a three-tier cascade.

First, native OS APIs. Windows API (WMI, Performance Counters, registry) because they're free, already there, and don't require external dependencies.

Second, specialized local utilities when present. CrystalDiskInfo for disk health, LibreHardwareMonitor for sensor data the OS API doesn't expose (chip temperatures, voltages, less common motherboard sensors). The agent detects their presence and parses their output, without bundling third-party code.

Third, graceful degradation. When nothing is available for a specific metric, it gets marked as unavailable instead of breaking the whole collection. A host with no dedicated GPU shouldn't lock up the agent.

This design matters because real environments are messy. Machines with locked BIOS, security agents that block WMI, hosts without admin privileges, outdated drivers. Each step in the cascade is a chance to still extract useful data where a monolithic approach would have already given up.

Resource footprint

The final binary sits in the low single-digit megabytes, with no runtime dependencies installed. RAM usage in normal operation stays low enough to run alongside real workloads without making itself noticed. That's exactly the point of a monitoring agent: being there without getting in the way.

Why it's worth the effort

Writing your own agent instead of adopting a pre-built one only makes sense in a few cases. When you need control over the shape of collection, for instance. Or when the target environment has specific constraints. Or when the code needs to be kept closed. In those cases, the Nim plus fallback-cascade combo yields a small, robust, independent product. This kind of project teaches a lot about cross-system interoperability, and the final result feels like something of your own, not a wrapper on top of a wrapper.
